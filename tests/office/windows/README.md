Windows C1 feasibility harness (S1940)
====================================

This is a default-off, harness-only measurement seam. It does not qualify C1 or
alter the shipped native worker launcher. Authority: runbooks `origin/main`
`b320acc07315ed76038091a2d71ca50288df7471`, Gate 2 C1 design deltas 2/3.

The `vz-office-windows-harness` crate can be checked independently of native C++:

```
rtk run cargo check --locked -p vz-office-windows-harness --features office-feasibility --target x86_64-pc-windows-msvc
```

Stage A launcher arguments:
`vz-office-windows-launch.exe WORKER confined|control REQUEST.json RESULT.json SCRATCH ATTACK_FILE [EXACT_INPUT ...]`.
All run files belong in a new private evidence root outside the checkout.
The worker is the actual `vz-parser-worker.exe`, built with `office-feasibility`.
The launcher never retries a refused confined launch as an unconfined process.
Positive controls are separately requested invocations.

Each confined invocation creates a fresh zero-capability LPAC profile, grants
its unique SID read/execute to the worker, read to exact input files and write
only to disposable scratch. Windows system runtime ACLs and the profile's own
OS-managed store are intrinsic AppContainer access, not host-folder grants.
Scratch receives a low-integrity label; only this disposable directory is
relabelled. No parent folder, host profile, runtime tree or loopback exemption
is granted. Startup failure is evidence of failure, never of confinement.

The process starts suspended with a three-pipe explicit handle list and a
minimal environment. An intentionally inheritable host-file handle is omitted.
The parent sets/reads back 1.5 GiB process and job committed-memory limits,
kill-on-close, active-process limit one, no breakaway, assigns the job and
checks the effective LPAC token before resuming. Any failure terminates the
worker. There is a deadline, no memory-kill sampler. Job peak commit, working
set and private commit are distinct fields. Temporary DACL grants are restored
and the AppContainer profile deleted after the worker is reaped. The suite
runner owns removal of scratch and host sentinel fixtures, including failures.

Windows has not been executed on the development Mac. Cross-checks establish
Rust/API type correctness only. LPAC startup, actual denials and full format
parity remain unproven until Windows evidence is collected.

Stage B
-------

Build the feature-gated **actual** parser worker and launcher, then run from
PowerShell with RTK on PATH:

```
rtk run cargo build --locked -p vz-parser-worker -p vz-office-windows-harness --features office-feasibility --bin vz-parser-worker --bin vz-office-windows-launch
rtk run python scripts/office-windows-feasibility.py --out "$env:KD_BRIDGE_JOB_EVIDENCE/run-1" --pdfium C:/exact/pinned/pdfium.dll
```

The runner has 99 planned rows. It creates a unique sentinel directory under
the user profile, temporary loopback/LAN TCP/UDP positive-control endpoints,
and CC0 ordinary TXT/Markdown/HTML/DOCX/XLSX/PDF files using the generator in
`tests/office/fixtures/windows_synthetic.py`. Generated bytes, sentinel paths,
requests, complete subprocess logs and raw worker responses remain under the
private run root. The profile sentinel is removed after the run. Only
`manifest.json` is suitable for artifact upload: parser content becomes a hash,
and host paths/IP addresses, request bodies and environment values are omitted.
The manifest records source/worker/launcher/PDFium hashes, OS build, runner
image version, all rows and reasons, API return/error codes and separate socket
creation results, job readbacks and committed-memory peaks.

Each row starts one unconfined control and one confined worker. The control
deliberately inherits the attack handle and joins a kill-on-close job allowing
breakaway, so child/escape/handle positives exercise the operation being denied.
Confined workers inherit **only** the three pipes. Scratch create/read/rename/
delete must succeed in both modes. All serialized parser response fields must
match, with a synthetic text oracle and two-page/two-sheet checks; empty or
failed parses cannot pass. These are extraction controls, not viewer coverage.

Memory runs retain allocations to a 2 GiB target, record the first refusal and
peaks with no memory sampler, then free them. Ordinary `confined` runs keep
both 1.5 GiB limits. `confined-process` raises only the diagnostic job ceiling
to 3 GiB; `confined-job` raises only the diagnostic process ceiling to 3 GiB.
Each isolates which kernel limit is being exercised, with readback validation.
Active-process limit one stays in force: the aggregate job test has one member
and makes no multi-child summation claim. A successful limit raise from inside
the worker fails its row. A mapping API that escapes job commit accounting will
also fail its row; the runner does not assume all allocations are charged.

AF_HYPERV, IPv6 routes, broker registrations and system-pipe access may be
unavailable. Binding an internet destination address is not a local-bind
positive, and TCP sendto / UDP listen may be unsupported. Such API control
failures are **unrun**, with raw error codes; they are never denial evidence.
Generic confined errors fail. Literal socket creation success fails even if
the subsequent connect is denied. The suite returns nonzero for **any** fail
or unrun row; no expectation of a green qualification result is built in.

Portable runner checks:

```
rtk run python scripts/office-windows-feasibility.py --self-test
```

Local full-worker cross-check was attempted but cannot build native C/C++
dependencies without the Windows SDK/MSVC headers on the Mac (`zstd-sys`:
missing `stdlib.h`, `assert.h`). The standalone harness's Windows-target check
and strict clippy succeed. Windows runtime/linking and actual-worker outcomes
remain unobserved locally.

Stage C
-------

`.github/workflows/office-feasibility-windows.yml` has one `windows-2022` job,
pushes only on `build/office-web-c1-feasibility-s1927` with harness/worker paths,
and `workflow_dispatch`. It reuses native CI's Python, MSVC, Vulkan, protoc,
pinned Rust and restored-CMake setup. RTK v1.1.0 is a SHA256-verified Windows
release. Only the existing pinned PDFium is fetched, without model/OCR assets.
Checkout credentials are not persisted; permissions are read-only.

The runner initializes every row as unrun **before the build**. The finalizer
keeps the most recent manifest, including partially completed runs, and checks
row completeness/status counts and format-response redaction even after a
failure. Setup/build failure leaves the all-unrun manifest in place. Only that
redacted JSON is uploaded; complete build/probe logs, raw frames/stderr and
synthetic fixtures stay in the runner's private temporary evidence root.
Capture exceeding the 32 MiB protocol/diagnostic budgets is marked as overflow
and fails the invocation; all captured bytes are retained privately. Job commit
peaks survive process exit; resident/private counters are also collected inside
the worker while allocations remain held.

No Windows CI outcome is asserted by this change. The operator reads the
artifact; failed or unavailable rows remain blocking feasibility gaps. The job
is expected to report literal socket success, unsupported API combinations,
missing routes/brokers or startup/parse failures honestly, without changing the
contract to make CI green.
